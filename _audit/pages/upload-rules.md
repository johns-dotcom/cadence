## 2. Summary

All four rule tables survive in NEW with label-scoped schemas and working CRUD — BOOK (`statement_category_rules`), SET ASIDE (`statement_dismiss_rules`), ARTIST (`statement_artist_rules` w/ `is_overhead`), NO INVOICE (`statement_no_invoice_rules`, vendor|category, equality-matched in completion) — and the ingest pipeline applies dismiss rules then category rules **after** auto-match fails (bank-statements.js:117-131), which structurally softens OLD's central trap (a rule can no longer shadow a matchable invoice at upload, and rule-booked rows remain rematch-eligible, bank-matching.js:272). What is gone is everything OLD built to make rules *safe to accept*: the entire rule-suggestions engine (repeated-decision mining, the invoice-census split into match/category/no-invoice/dismiss/artist, the provable `bookPatternFor` check, clears/conflicts/also-matches/covers-N-of-M disclosures), the `annotate=1` per-rule leak report (queue_rows/queue_usd/ledger_payees with real_invoices + clears) and its pair-it action, the both-halves category+no-invoice write, and the never-invoiced evidence test behind category candidates. The organizing question — "will this line ever have an invoice behind it?" — has no surface; NEW's chips let you write the answers but nothing prevents, warns about, or even reveals the wrong ones: an unpaired BOOK rule quietly feeding the needs-invoice queue is exactly as invisible in NEW as it was in OLD *before* BkRules existed (measured then: 6 of 10 rules leaking 137 rows / $26,528). Totals: **13 defects (2 P1 · 5 P2 · 5 P3 · 1 P4), 5 intentional divergences.**

## 4. Interaction & behavior parity

- **Six parallel loads** (suggestions, annotated category rules, dismiss, artist, no-invoice, completion — BkRules.jsx:53-63) → NEW: RulesPanel loads artist + no-invoice (:462-465) and receives `completion` as a prop; category/dismiss arrive only inside `GET /bank-statements/:id`. No suggestions call exists to make.
- **acceptNoInvoice → POST /category-rules `{pattern, category, no_invoice_pattern}`** — OLD writes BOTH halves atomically, rolling the booking rule back if the no-invoice insert fails (statements.js:8628-8663). NEW has **no standalone category-rule create at all**; the only writer is book-with-rule (`req.body.rule` on `/txns/:id/book`, bank-statements.js:618-621), which writes the one half and can never pair (DEF-RUL-04, DEF-RUL-08).
- **acceptStopAsking / markNoInvoice** — survive as `addNoInv(scope, pattern)` chips (BankMatching.jsx:474-477) hitting POST `/bank-matching/no-invoice-rules`; but OLD's confirm dialogs quantify what leaves the queue (`queue_rows`/`fmt(queue_usd)`, BkRules.jsx:119-123,156-158) and NEW asks nothing and reports nothing (toast only).
- **pairRule** — the close-the-leak flow (safe vs invoicing payee split, `clears ?? rows` over-delivery accounting, batch `patterns` write, refusal when every payee really invoices — BkRules.jsx:168-196) has no NEW counterpart; POST no-invoice-rules takes a single `pattern` only (bank-matching.js:614).
- **Remove** — OLD confirms with consequences ("Future statements stop applying it. Nothing already recorded changes.", :198-205); NEW deletes immediately, no confirm, on both surfaces (BankMatching.jsx:478-480; BankStatements.jsx:189).
- **Artist rules** — CRUD + `is_overhead` + upsert-on-pattern parity (bank-matching.js:574-600 ≈ statements.js:8836-8855, incl. the artist-or-overhead validation and ≥3-char pattern). Retro application diverges hard: OLD writes history **only to explicitly-reviewed `entry_ids`**, re-verified server-side, precisely because a substring sweep misattributes ("TONE" ⊂ "Tone Pay, Inc", statements.js:8858-8895); NEW `retro:true` sweeps by `LIKE '%pattern%'` over descriptor+payee_guess (bank-matching.js:587-596) and the UI defaults retro ON (BankMatching.jsx:461) (DEF-RUL-06). NEW also skips per-row `autoLinkRelease` (OLD :8892; no equivalent call in cadence bank-matching — grep clean) (DEF-RUL-07). OLD's requested-vs-written `skipped` accounting (:8899-8910) is gone (folded into DEF-RUL-06).
- **No-invoice rule matching in completion** — OLD's venRules matches `e.payee` OR `bt.payee_guess` by equality (the documented over-delivery: one accept promised 3, cleared 14 — statements.js:7300-7304); NEW's `ruleHit` tests only `exp_payee || payee_guess` — the fallback chain, not both (bank-matching.js:123-128), so a rule written for the bank descriptor misses rows whose ledger payee differs and vice versa (DEF-RUL-12).
- **category_candidates** — OLD requires that **no vendor in the category has ever sent an invoice** (everInvoiced census over `invoice_number`, statements.js:8552-8572) and ships n + $value + vendor count; NEW counts booked-not-expected rows per category, top-12 by count, no invoice test, no value (bank-matching.js:151,177) (DEF-RUL-05).
- **Deep links** — OLD's "Work these →" rows link into Bank Matching pre-filtered; NEW's chips act in place and nothing routes rules-context → queue-context (folded into DEF-RUL-01).
- **Error surfacing** — OLD banner + retry, explicit "an empty rule list reads as no rules exist" (:70-76); NEW `.catch(() => {})` on both RulesPanel loads renders exactly that silent empty list (:463-464) (DEF-RUL-13).

## 5. Server/data parity

- Schemas ported with label scoping + per-label unique indexes (`(label_id, scope, LOWER(TRIM(pattern)))` no-invoice, `(label_id, LOWER(pattern))` artist — index.js:1753-1777); `is_overhead` present. Parity.
- Ingest applies dismiss rules (substring), then auto-match, then category rules (substring) booking via `bookEntry` with `match_method='rule'` (bank-statements.js:88-131). OLD books rule rows as `match_method='created'`; NEW's completion treats `'rule'` and `'created'` identically (bank-matching.js:141) and rematch-candidates covers both (:272). Parity of effect, softer trap (INT-worthy improvement in ordering).
- POST no-invoice-rules: no `patterns` array (OLD's all-or-nothing batch write, statements.js:8711-8730), no scope error (silently coerces to 'vendor', bank-matching.js:613), no ≥2-char floor, `ON CONFLICT DO NOTHING`, no audit (DEF-RUL-09/10).
- Rule creation via dismiss/book slices the payee to 120 chars but has **no minimum length** — a 1-2-char `payee_guess` writes a substring rule that auto-dismisses/auto-books broad swathes of future uploads; OLD enforces ≥3 on every rule-writing endpoint (statements.js:8622,8679,8846) (DEF-RUL-08 covers dismiss/category; artist POST does enforce ≥3, bank-matching.js:577).
- OLD audits every rule mutation via `audit(...)` (statements.js:8666,8683,8731,8897); NEW rule CRUD writes no activity/audit records at all (only book/dismiss row actions log) (DEF-RUL-10).
- OLD `/completion` reports a distinct `creator` bucket and `left_all`/`left_all_value` headline; NEW folds creator matches into `booked_expected` (:155) and derives left-per-statement only — invoice-backed semantics preserved. Not a rules-page defect; noted for cross-reference.

## 7. Intentional divergences

- Label scoping on all four rule tables + per-label unique indexes; `requireAdmin` router gates replacing per-endpoint `isStrictAdmin` (same effective audience).
- Ingest ordering — category rules apply only AFTER auto-match fails (bank-statements.js:117-131), and rule-booked rows stay rematch-eligible (bank-matching.js:272) — structurally mitigates OLD's "rule permanently converts matchable payments into rematch work" trap at the pipeline level (the reporting gap remains, see DEF-RUL-02/03).
- Row-level `no_invoice` flag + per-txn/bulk endpoints (bank-matching.js:627-642) — additive answer-one-row capability alongside the rule tables.
- Rules panel lives inside the Bank Matching work surface rather than a separate setup page — a layout philosophy choice (OLD split SETUP from WORK deliberately; the *missing capabilities* are itemized above, the placement itself is a call cadence is entitled to).
- `match_method='rule'` distinguishes rule-booked from hand-booked rows (OLD reused 'created') — finer provenance, handled equivalently by completion/rematch.

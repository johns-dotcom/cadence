# Recoupment Planning — parity audit

Companion to `_audit/pages/recoupments.md` (index/detail surface). Design-token deltas are covered by RC-1..RC-6 in `_audit/01-design-system.md` and are not re-reported per element.

## 1. Files compared (purpose & pairing)

| Side | Client | Server |
|---|---|---|
| OLD (truth) | `boom-dashboard/client/src/pages/RecoupmentsPlanning.jsx` (1,755 lines) + `lib/recoupmentPlan.js` (localStorage plan store), `components/FilePreview.jsx`, `FlagButton.jsx`, `CommentThreadButton.jsx`, `utils.js` (`fmtMoney`, `totalsToUsd`, `usdSuffixForEntry`, `withoutUnreviewedBankRows`), `context/FxRatesContext` | `boom-dashboard/server/routes/bookkeeping.js` — no dedicated planning endpoint: the page reads `GET /bk/entries?status=approved&deleted=false` (RecoupmentsPlanning.jsx:166) and commits via per-item `PUT /bk/entries/:id { ufr:'Yes', recoupment_label }` (:746, :812); supporting: `GET/PUT /bk/recoupments/notes` (page note, :84/:97), `GET/PUT /bk/artist-meta` (flags, :109/:123), `POST /bk/entries/:id/flag` (:483), `GET /bk/comments?ids=` (:661), `POST /bk/entries/:id/split` (:633), `DELETE /bk/entries/:id` (:556); ready-for-planning markers live in `bookkeeping.js` artist-level (:9968-9977) and song-level (:10165-10178) |
| NEW | `cadence/client/src/pages/RecoupmentPlanning.jsx` (120 lines) | `cadence/server/routes/financials.js`: `GET /financials/planning` (:280-298), `POST /financials/recoupments/ufr-bulk` (:302-316); artist meta upsert `POST /recoupments/artist-meta` (:351-376, not called from this page) |

**Purpose drift up front:** OLD's page is the staging area for a *hand-curated working set* — items explicitly pushed from the Recoupments Pending tab ("Add to plan"), held in localStorage (`recoupmentPlan.js:16` key `recoupment_plan_v2`), grouped/LABELED into named upload batches, then bulk-stamped UFR with each item's `recoupment_label`. NEW's page is a *full-pool browser*: `GET /financials/planning` returns **every** approved recoupable non-UFR row in the label (financials.js:282-290) and the operator selects + commits from that. There is no staging step, no plan store, and no labels.

- OLD: `/recoupments/planning` inside `TabbedShell family="recoupments"` (boom App.jsx:231) — part of the Recoupments tab family, with an explicit "Back to Recoupments" pill on the page (RecoupmentsPlanning.jsx:899-904). ## 5. Behavior/interactions diff

- **Staging model (DEF-RPLAN-01, P1).** OLD: plan = `{expenseId: label}` in localStorage (`recoupmentPlan.js:16-33`), written by Recoupments' "Add to plan", auto-pruned when rows become ineligible (:197-221), rehydrated on window focus (:184-188), reset via "Reset plan" with confirm (:778-784). NEW has none of this — the page *is* the whole eligible pool, so curation done today (which items belong to this month's batch) evaporates; only the transient checkbox selection expresses it, and it resets on every load (`setSel(new Set())` in `load`, :24). NEW's Recoupments page has no "Add to plan" control (grep: zero hits).
- **Labels (DEF-RPLAN-02, P1).** OLD's entire grouping/labeling system — per-item label chips + anchored menu (:678-696, :1706-1752), bulk Move-to-label + New label… (:1053-1074), group-by-label view mode (:365-394), unlabeled counters everywhere (:966-974, :1190-1192), and `recoupment_label` stamped at commit (:814) so statements group by upload batch — is absent. No schema column exists in cadence.
- **Commit (DEF-RPLAN-15, P2 + DEF-RPLAN-03, P1 server side).** OLD offers two grains: header "Done · Mark N UFR" commits every *active* (non-deferred) plan item (:790-865) and the bulk bar's "Mark N UFR" commits just the selection (:729-776); both run 6-way bounded per-item PUTs, report per-item failures in the banner, keep failures staged for retry, and full-commit navigates back to `/recoupments`. Confirm strings explain the statement-landing consequence and the deferred count. NEW: selection-only commit, single bulk UPDATE, generic `Failed` toast on error, stays on page, confirm string is one line (:50). Server risks in §3.
- **Save for later (DEF-RPLAN-16, P3).** OLD: per-artist bookmark persisted in localStorage `recoupment_plan_deferred` (:143-151); deferred cards remain fully visible/inspectable in their own bottom section with count/totals/hint (:1196-1221); Done's confirm discloses "(N saved for later stay in the plan)" (:795); "everything deferred" gets its own explanatory line (:1202-1206). NEW: in-memory `Set` (:21) — **lost on reload**; deferring hides the artist's songs/items entirely (:76 renders nothing when deferred) and clears their selection; no totals, no disclosure in the confirm.
- **Selection affordances (DEF-RPLAN-22, P3).** OLD: page-level Select all (cards view, :1127-1136), artist-level Select all (:1259-1266), song-section header checkbox (:1295-1308), category checkbox + click-row-to-toggle-bucket (:1332-1356), row click toggles selection (:1373). NEW: per-song group checkbox (:82) and per-row checkbox (:88) only; row click does nothing.
- **Row actions** — each its own defect (§7): Recoup toggle w/ optimistic rollback (:506-515) and per-row UFR toggle carrying the plan label (:517-530) [DEF-RPLAN-07]; cobrand toggle w/ category=Marketing mirror + rollback (:534-547) [DEF-RPLAN-08]; split modal (:589-650) [DEF-RPLAN-09]; invoice FilePreview with split-parent fallback + own-file preference (:277-293, :1495-1513) [DEF-RPLAN-10]; artist FlagButton on cards + per-expense flag w/ inline amber reason strip (:104-138, :473-496, :1471-1479) [DEF-RPLAN-11]; CommentThreadButton + inline sky comment strips bulk-fetched in one request (:655-672, :1483-1491) [DEF-RPLAN-12]; soft-delete w/ confirm + plan prune (:552-565) [DEF-RPLAN-13]; bulk Set song… prompt (:570-583) [DEF-RPLAN-14]; socials chip w/ platform+amount display and parent fallback (:44-54, :288-293, :1455-1467) [DEF-RPLAN-19].
- **Deep links (DEF-RPLAN-17, P3).** OLD: `?artist=<key>` URL-backed drill-down (:301-308) and `?focus=<expenseId>` from the Ledger — auto-selects the artist, scrolls, amber-spotlights 3.2s (:313-326). NEW: neither param; NEW rows link *out* to `/ledger?focus=` (:93) but nothing links in.
- **Ready-for-planning flow (DEF-RPLAN-20, P3).** The markers exist to answer "which artists/songs are ready to stage." OLD surfaces them on the Recoupments index (filter + chip) feeding Add-to-plan; NEW's planning page — the surface that replaced staging — never reads `artist_meta.ready_for_planning` (no badge, sort, or filter), so the marker set on NEW Recoupments (:175) leads nowhere.
- **Priority handling — no difference on this surface.** Neither OLD nor NEW planning page reads artist priority; priority lives on the Recoupments index both sides (see recoupments.md DEF-RECOUP-35 for the subtab gap).
- **Copy list (DEF-RPLAN-18, P4).** OLD exports the grouped plan as a plain-text outline to the clipboard w/ per-group totals + grand total, prompt fallback (:871-895). NEW: none.
- **Ordering (DEF-RPLAN-24, P4).** OLD artist cards sort by staged USD desc (:347); song sections by spend desc with `(no song)` sunk (:436-440); items by payment/invoice date desc. NEW renders artists in server order — alphabetical `LOWER(artist)` (financials.js:288) — and songs alphabetically; item date order matches.
